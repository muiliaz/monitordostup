# Монитор доступности сайтов

Тестовое задание: сервис, который периодически проверяет доступность URL,
ведёт историю и журнал инцидентов, шлёт письма при падении/восстановлении и
показывает live-статусы на панели и на публичной странице.

Почему проект устроен именно так — в логе решений [DECISIONS.md](DECISIONS.md):
запись на каждый этап, с временной меткой, принятыми решениями и замерами.
Как убедиться, что всё работает, — раздел [«Как проверить»](#как-проверить-что-всё-работает).

## Архитектура

| Сервис            | Что это                                                    | Порт на хосте |
|-------------------|------------------------------------------------------------|---------------|
| `postgres`        | PostgreSQL 16 — единственное хранилище                     | —             |
| `backend`         | Node.js 22 + TypeScript + Fastify + Prisma: API, планировщик, SSE, почта | 3000 |
| `frontend`        | React + TypeScript + Vite, отдаётся nginx, `/api` проксируется на backend | 8080 |
| `maildev`         | Эмулятор SMTP с веб-интерфейсом для просмотра писем        | 1080          |
| `target-emulator` | Заглушка «проверяемых сайтов» с управляемым поведением     | 4000          |

### Почему Node.js для backend

Домен — десятки параллельных I/O-bound HTTP-проверок с таймаутами. Event loop
Node.js естественно подходит под эту нагрузку: каждая проверка — независимая
асинхронная задача, медленный или зависший сайт просто держит открытый сокет
и не блокирует ни другие проверки, ни обработку запросов интерфейса. Пул
потоков для этого не нужен.

## Как развернуть локально

### Пререквизиты

- Docker 24+ с Docker Compose v2 (проверялось на Docker 29.5, Compose v5.1)
- Свободные порты 8080, 3000, 1080, 4000 (меняются в `.env`)
- Node.js 22+ — только если нужно запускать скрипты проверки/разработку вне Docker

### Запуск

```bash
cp .env.example .env
docker compose up --build
```

- Панель: http://localhost:8080 (логин/пароль — `ADMIN_USERNAME` / `ADMIN_PASSWORD` из `.env`)
- Публичная страница статуса, без входа: http://localhost:8080/status
  (показывает проверки с флагом «публичная»)
- Письма о падении и восстановлении: адреса задаются у группы на странице
  «Группы». Проверки без группы шлют на `DEFAULT_ALERT_EMAILS` из `.env`.
  Все письма видны в MailDev.
- MailDev: http://localhost:1080
- Backend healthcheck: http://localhost:3000/api/health

### Наполнить панель для демонстрации

```bash
node scripts/demo-setup.mjs
```

Складывает проверки эмулятора (на них построены сценарии из раздела ниже) в
группу «Демо: эмулятор» и заводит группу «Реальные сайты» с несколькими
публичными сторонними адресами: `example.com`, Cloudflare, Google
(`generate_204`, ожидается код 204), GitHub API, Telegram, Википедия и
намеренно медленный `httpbin`. Интервалы вежливые — от минуты до пяти:
это чужие серверы.

Скрипт идемпотентный: проверки и группы ищутся по имени, существующие
обновляются на месте, поэтому история, инциденты и графики уже заведённых
проверок не теряются. История у новых проверок наполняется по-настоящему,
ничего не досыпается: первые сутки графики за неделю и месяц будут почти
пустыми.

## target-emulator: эндпоинты

Заглушка «проверяемых сайтов». Из контейнеров доступна как
`http://target-emulator:4000/...`: этот адрес указывается в проверках. С хоста —
`http://localhost:4000/...`.

| Эндпоинт | Поведение |
|---|---|
| `GET /ok` | `200`, тело содержит `status: ok` (для проверки подстроки) |
| `GET /slow?ms=3000` | `200` после задержки (до 10 мин) |
| `GET /error?code=500` | отвечает указанным кодом |
| `GET /timeout` | никогда не отвечает |
| `GET /flaky?rate=0.5` | `500` с вероятностью `rate`, иначе `200` |
| `GET /switch/<name>` | ведёт себя по текущему режиму цели `<name>` (по умолчанию `ok`) |
| `PUT /control/switch/<name>` | сменить режим: `{"mode":"ok"\|"error"\|"slow"\|"timeout","code":503,"ms":5000}` |
| `GET /control/switch`, `DELETE /control/switch` | текущие режимы / сбросить все в `ok` |
| `GET /control/hits?path=/ok&since=<ISO>` | журнал обращений к целям |
| `DELETE /control/hits` | очистить журнал |

Пример: «уронить» сайт и поднять обратно, не меняя саму проверку.

```bash
curl -X PUT localhost:4000/control/switch/site-a -d '{"mode":"error","code":503}'
curl -X PUT localhost:4000/control/switch/site-a -d '{"mode":"ok"}'
```

Query-параметры, которые эндпоинт не использует, игнорируются. Так 50
проверок могут смотреть на `/ok?n=1` … `/ok?n=50` и при этом различаться в
журнале обращений.

## Как проверить, что всё работает

```bash
docker compose up -d --build   # если ещё не запущено
node scripts/verify.mjs        # ~4 минуты, нужен Node.js 22+ на хосте
```

Скрипт проверяет каждый пункт «Ожидаемого поведения» из задания на живой
системе: через API панели, управляемые цели эмулятора, MailDev и SSE-потоки.
По каждому сценарию печатается PASS или FAIL со значениями замеров; код
выхода 1, если хоть что-то не сошлось.

| Сценарий | Что доказывает |
|---|---|
| `crud` | проверку можно добавить, приостановить, возобновить, изменить, запустить вручную и удалить |
| `live` | статусы на панели и публичной странице меняются сами, без перезагрузки |
| `threshold` | одна неудача — не падение; инцидент открывается после порога и закрывается с длительностью |
| `alerts` | письмо при падении, письмо при восстановлении, между ними ничего |
| `maintenance` | в окне обслуживания проверки идут и статус виден, письма не уходят; после окна лежащий сайт даёт письмо |
| `overlap` | проверка, которая длится дольше интервала, не запускается параллельно сама себе |
| `load` | 50 проверок с интервалом 30 с не мешают друг другу, медленный сайт не задерживает остальные, панель отвечает |
| `month` | история за месяц открывается быстро на 864 000 результатов |
| `public` | публичная страница показывает только разрешённое, админский API закрыт |
| `restart` | после перезапуска проверки продолжаются, простой виден пробелом, а не падением |

Флаги: `--quick` (пропустить `overlap`, `load`, `month`, `restart`),
`--only=alerts,public` (выборочно).

Скрипт заводит собственные группы и проверки с именами `verify-<время>-…`
и удаляет их за собой, поэтому его можно запускать на стенде, где уже есть
ваши проверки. Сценарий `restart` на 45 секунд останавливает контейнер
`backend`, а `month` засевает историю напрямую в Postgres через
`docker compose exec`.

Пример вывода одного сценария:

```
▶ load: 50 проверок с интервалом 30 с не мешают друг другу, медленный сайт не задерживает остальные, интерфейс отвечает
      · создано 50 быстрых проверок и одна медленная (20 с)
      · за 95 с: 200 запросов к быстрым целям по 50 разным адресам
      · интервал между запросами к одной цели: максимум 30.1 с при заданных 30 с
      · GET /api/checks во время нагрузки: медиана 9 мс, максимум 13 мс
      ✓ ни одна цель не ждала дольше 40 с между опросами (максимум 30.1 с)
  PASS load (96.6 с)
```

## Текущее состояние проекта

Репозиторий: https://github.com/muiliaz/monitordostup

Работает всё, что перечислено в задании; каждый пункт «Ожидаемого поведения»
проверяется скриптом из раздела выше (10 из 10).

**Что сделано**

| Из задания | Где |
|---|---|
| Список проверок: URL, интервал 30 с — 1 ч, таймаут, ожидаемый код, ожидаемая строка в теле | страница «Проверки», форма проверки |
| Добавить, приостановить, возобновить, удалить, запустить вручную | кнопки в строке проверки |
| Группы проверок с общим статусом | страница «Группы», заголовки групп на панели |
| Панель: состояние, время ответа, время последней проверки, длительность падения | страница «Проверки» |
| История за сутки/неделю/месяц: график времени ответа, процент доступности за период и доля неудачных проверок по корзинам | блок «История» на странице проверки |
| Журнал инцидентов: начало, конец, длительность | страница «Инциденты» и блок на странице проверки |
| Окна обслуживания по проверке или группе | страница «Обслуживание» |
| Адреса оповещений, свои для каждой группы | страница «Группы»; проверки без группы шлют на `DEFAULT_ALERT_EMAILS` |
| Публичная страница статуса без входа | `/status` |
| Статусы меняются без перезагрузки | SSE: `/api/stream` и `/api/public/stream` |
| Письмо при падении и при восстановлении, между ними тишина | MailDev, `backend/src/alerts/` |
| Порог: одиночный сбой не падение | две неудачи подряд (`FAILURE_THRESHOLD`) |
| Проверка не запускается параллельно сама себе | захват строки в БД, `backend/src/scheduler/` |
| 50 проверок × 30 с без взаимных помех | замер в сценарии `load` |
| История за месяц открывается быстро | почасовая свёртка `check_results_hourly` |
| После перезапуска — пробел в истории, а не падение | `next_run_at` в БД, пропущенные слоты не догоняются |

**Чего нет и почему**

- **Одна учётная запись администратора** (логин и пароль из `.env`).
  Задание разрешает любую модель входа; многопользовательский режим,
  роли и регистрация не делались.
- **Выход не отзывает cookie на сервере:** cookie просто перестаёт
  отправляться браузером, а её срок жизни — 7 дней. Для одной локальной
  учётки приемлемо, для продакшена нужен список отозванных сессий.
- **Публичный поток SSE открыт без входа и без ограничения числа
  соединений.** На реальном сервере нужен лимит на IP на прокси.
- **Один экземпляр backend.** Проверку захватывает атомарный `UPDATE …
  WHERE is_running = false`, то есть сама выдача работ конкурентна, но при
  старте процесс снимает все оставшиеся блокировки, считая их следами
  своего прошлого запуска, — со вторым экземпляром это отняло бы у него
  работу. Плюс шина live-событий живёт в памяти процесса: вкладки на
  разных экземплярах видели бы разные события. Для горизонтального
  масштабирования нужны аренда блокировок по времени и внешний pub/sub.
- **История не чистится:** сырые результаты хранятся без ограничения
  срока. Свёртка делает графики быстрыми, но место занимает сырая
  таблица.
- **Часы сервера.** Если время сервера прыгнет назад, уже посчитанные
  `next_run_at` окажутся в будущем и проверки будут стоять до выравнивания
  часов. На сервере с NTP так не бывает; в Docker Desktop после сна
  Mac — бывает (описано в логе решений).
- **Корзины свёртки — целые часы UTC.** В поясах со сдвигом не на целый
  час (например, +5:30) границы часовых корзин на графике не совпадают с
  местными часами.
- **На графиках нет перцентилей** (p95): из почасовых сумм их не
  восстановить, для этого нужно хранить распределение.
- **Больше шести вкладок одновременно** упрутся в лимит соединений
  браузера на один хост по HTTP/1.1: седьмая вкладка не получит поток,
  пока не закроется одна из предыдущих.
- **Браузерных end-to-end тестов нет.** Логика покрыта unit-тестами
  (`npm test` в `backend/`), поведение целиком — скриптом
  `scripts/verify.mjs`, который работает по сети, как клиент. Интерфейс
  проверялся вручную и снимками в headless Chrome.

## Что сделали бы следующим заходом

- **Срок хранения истории и чистка** сырых результатов, когда есть
  свёртка: сейчас таблица растёт неограниченно.
- **Защита от прыжка часов назад:** перепланировать проверку, если её
  `next_run_at` дальше, чем «сейчас + интервал».
- **Ограничение публичного потока:** лимит соединений и запросов на IP.
- **Несколько экземпляров backend:** внешний pub/sub для live-событий.
- **Перцентили времени ответа** на графиках.
- **Оповещения не только почтой:** вебхуки, мессенджеры, тихие часы.
- **Playwright** для браузерных сценариев: две вкладки, формы, графики.
- **Поиск и постраничный вывод** в списке проверок: при сотнях проверок
  одна страница станет неудобной.

## Шаблоны, генераторы, чужой код

Шаблоны и генераторы не использовались: ни `create-vite`, ни `nest new`,
ни готовые стартовые репозитории. Конфигурации, Dockerfile, схема БД и весь
код написаны под эту задачу.

Чужое в проекте — это пакеты из npm и образы из Docker Hub: Fastify,
Prisma, Zod, nodemailer, React, React Router, TanStack Query, Vite,
Postgres, nginx, MailDev. Графики нарисованы вручную на SVG, библиотека
графиков не подключалась. Выбор каждого пакета объяснён в `DECISIONS.md`.
