## 2026-09-18 14:05 — Этап 1: scaffold, docker-compose, заготовки документации

**Сделано.** Монорепозиторий из трёх приложений (`backend/`, `frontend/`,
`target-emulator/`) и `docker-compose.yml` с пятью сервисами. Backend
отвечает на `/api/health` с проверкой соединения с БД; frontend его вызывает.

**Решения:**

- **Монорепо без workspaces.** Три независимых `package.json`, у каждого свой
  Dockerfile. Общего кода между клиентом и сервером нет (требование:
  общаются только по сети), значит npm workspaces дали бы только сложность
  в Docker-сборке.
- **Frontend раздаётся через nginx, `/api` проксируется на backend.** Один
  origin для браузера: не нужен CORS, cookie-сессия работает без
  `SameSite=None`, а `EventSource` (который не умеет ставить заголовки)
  автоматически отправляет cookie. Для SSE в nginx отключена буферизация и
  увеличен `proxy_read_timeout`, иначе события приходили бы пачками или
  соединение рвалось бы через 60 секунд.
- **Миграции применяются при старте backend** (`prisma migrate deploy`), чтобы
  запуск оставался одной командой без ручных шагов.
- **Версии пакетов.** Prisma закреплена на 6.19 (классический
  `prisma-client-js`): в 7.x изменилась модель подключения (driver adapters,
  `prisma.config.ts`), а выигрыша для этой задачи нет. TypeScript ~5.9, а не
  7.x (нативный компилятор): свежий мажор, лишний риск. Fastify 5, React 19,
  Vite 8 — актуальные стабильные.
- **Образы на Node 22 LTS.** Backend — `bookworm-slim`, а не alpine: движки
  Prisma стабильнее работают с glibc/openssl 3. target-emulator не имеет
  зависимостей и запускает `.ts` напрямую за счёт встроенного в Node 22.18+
  type stripping, отдельный шаг сборки не нужен.
- **Postgres наружу не публикуется.** Проверочным скриптам он не нужен (всё
  идёт через API), и так не будет конфликта с локальным Postgres на 5432.

## 2026-09-18 14:35 — Этап 2: CRUD проверок и групп, admin-вход

**Сделано.** Таблицы `groups` и `checks` (первая миграция), REST API:
`/api/checks` (список, карточка, создание, изменение, pause/resume, удаление),
`/api/groups` (CRUD, вычисляемый статус группы), `/api/auth/*` (вход/выход).
Frontend: страница входа, панель проверок по группам, управление группами и
адресами оповещений.

**Решения:**

- **Авторизация вошла в этот этап, а не отдельным.** Без неё CRUD-эндпоинты
  пришлось бы закрывать задним числом. Сессия — подписанная httpOnly-cookie
  (`@fastify/cookie`), внутри только время истечения: учётка одна, хранить
  в cookie больше нечего, таблица сессий не нужна. Выбрана cookie, а не JWT
  в заголовке, потому что `EventSource` не умеет ставить заголовки, а cookie
  отправляет сам. Это пригодится на этапе SSE. Логин и пароль сравниваются
  через `timingSafeEqual` по sha256-хэшам, чтобы не было утечки по времени
  и сравнивались буферы одинаковой длины. Цена решения: logout не отзывает
  уже выданную cookie на сервере. Для одной локальной учётки это приемлемо,
  записано в ограничения.
- **Модель: добавлены поля сверх ориентира из ТЗ:** `name`, `last_checked_at`,
  `last_response_time_ms`, `status_changed_at` (от него считается
  длительность текущего падения), `locked_at` (чтобы снимать зависший lock).
  Состояние мониторинга денормализовано в `checks`, чтобы панель
  отрисовывалась одним запросом без обращения к истории.
- **Все даты — `timestamptz`.** Prisma по умолчанию создаёт `timestamp`
  без зоны. Для агрегации истории по суткам и часам в SQL (этап 10) нужна
  однозначная временная зона.
- **Индекс `(is_paused, next_run_at)`** — под запрос планировщика «какие
  проверки пора запускать».
- **Статус группы вычисляется, а не хранится.** Группа `down`, если упала
  хотя бы одна активная проверка. `up` — только если все активные работают.
  Проверки на паузе не учитываются. Хранить его значило бы синхронизировать
  при каждой смене статуса проверки, а посчитать дёшево.
- **Удаление группы не удаляет проверки** (`ON DELETE SET NULL`): потерять
  проверки вместе с историей из-за удаления группы — неожиданное поведение.
- **Пауза и возобновление — отдельные действия, а не поле формы.** Resume
  ставит `next_run_at = now()`, чтобы проверка сразу запустилась, а не ждала
  устаревшего времени.
- **Таймаут до 60 с при минимальном интервале 30 с — осознанно.** Проверка
  может выполняться дольше своего интервала, и это поведение должно
  обрабатываться защитой от наложения (этап 4), а не запрещаться формой.
- **Валидация — zod** (v4). Вместо JSON-схем Fastify: из одной схемы сразу
  получаются и проверка, и TypeScript-тип, и нормализация (пустая подстрока
  превращается в `null`, адреса приводятся к нижнему регистру и
  дедуплицируются). Ошибки Prisma приводятся к HTTP-кодам: 404, 409, 400.
- **Миграции генерируются через `prisma migrate diff`** (схема → SQL), без
  живой БД на хосте: Postgres намеренно не опубликован наружу.

## 2026-09-18 14:51 — Исправление после ручной проверки этапа 2: выход из панели

**Проблема (нашёл пользователь при ручной проверке).** После «Выйти» панель
оставалась на экране с «Загрузка…» или ошибкой. Форма входа появлялась
только после перезагрузки страницы.

**Причина.** `queryClient.clear()` удалял кэш запроса `/auth/me`, но не
перезапрашивал его, поэтому интерфейс не узнавал, что сессии больше нет.

**Решение.**
- При выходе запрос `me` явно сбрасывается и перезапрашивается
  (`resetQueries`). Его 401 переключает интерфейс на форму входа, и только
  после этого удаляется остальной кэш.
- Глобальный обработчик: любой 401 от API (истёкшая или удалённая cookie)
  перепроверяет `me`. Ретраи на 401 отключены.
- Сам `me` из этого обработчика исключён. Первая версия исправления
  зацикливалась: 401 на `me` снова инвалидировал `me`. Нашёл по
  бесконечной серии запросов `/api/auth/me` в логах backend.

**Как проверено.** Headless Chrome: вход, клик «Выйти» → сразу форма входа,
повторных запросов нет.

## 2026-09-18 14:53 — Этап 3: target-emulator

**Сделано.** HTTP-сервер без зависимостей, эмулирующий проверяемые сайты:
`/ok`, `/slow?ms=`, `/error?code=`, `/timeout`, `/flaky?rate=` из ТЗ, а также
управляемые цели `/switch/<name>` и журнал обращений `/control/hits`.

**Решения:**

- **Управляемые цели `/switch/<name>` сверх ТЗ.** Сценарий «упал →
  восстановился» (письмо при падении и при восстановлении) требует, чтобы
  один и тот же URL сначала отвечал ошибкой, а потом снова 200. Со
  статическими эндпоинтами пришлось бы менять URL проверки, то есть
  редактировать саму проверку посреди инцидента, а это другой сценарий.
  Режим меняется через `PUT /control/switch/<name>`, по умолчанию `ok`.
  Это же нужно для автоматического скрипта доказуемости (этап 11).
- **Журнал обращений `/control/hits`** — независимое от backend
  доказательство параллельности: по времени прихода запросов на стороне
  «сайта» видно, что `/ok` опрашиваются по расписанию, пока `/slow` висит.
  Кольцевой буфер на 20 000 записей, чтобы при 50 проверках раз в 30 с
  память не росла бесконечно (это ~3,3 часа истории).
- **Эндпоинты `/control/*` в журнал не пишутся** — это управление, а не
  проверки.
- **`/timeout` действительно никогда не отвечает**, а не спит какое-то
  большое время. `server.requestTimeout = 0`, иначе Node сам закрыл бы
  соединение через 300 с, а в эмуляторе это соединение закрывает таймаут
  проверяющего. Для `/slow` таймер снимается при закрытии сокета клиентом,
  чтобы брошенные запросы не копились.
- **Без зависимостей и без сборки**: `.ts` запускается напрямую за счёт type
  stripping в Node 22.18+. Сервис должен быть тривиальным и очевидно
  «чужим» для backend — никакого общего кода.
- **Лишние query-параметры игнорируются**, поэтому 50 проверок могут
  указывать на `/ok?n=1…50` и различаться в журнале.

**Как проверено.** Локально через node: все режимы и коды ответа; 5
параллельных `/ok` ответили за ~1 мс, пока `/slow?ms=3000` ещё висел;
переключение режимов `/switch`; журнал с фильтрами. Docker-образ собирается,
внутри Node 22.23.

## 2026-09-18 18:53 — Этап 4: ядро планировщика с защитой от наложения

**Сделано.** In-memory планировщик в процессе backend: тик раз в секунду,
атомарный захват «созревших» проверок, HTTP-проверка с таймаутом, запись
последнего результата и счётчиков подряд идущих успехов и неудач, расчёт
`next_run_at`. Ручной запуск `POST /api/checks/:id/run`, статистика
`GET /api/scheduler/stats` (задержка старта и длительность за 5 минут),
корректная остановка по SIGTERM. Юнит-тесты на расчёт следующего слота.

**Решения:**

- **Гонка при двойном тике решена на уровне БД, а не флагом в памяти.**
  Захват — один SQL:
  `UPDATE checks SET is_running = true … WHERE id IN (SELECT … WHERE is_running = false AND next_run_at <= now FOR UPDATE SKIP LOCKED) RETURNING …`.
  Строки блокируются в подзапросе, поэтому два параллельных тика (или два
  процесса backend) никогда не получат одну и ту же проверку: второй
  пропускает заблокированные строки, а после коммита первого видит
  `is_running = true`. Ручной запуск берёт тот же lock условным
  `UPDATE … WHERE is_running = false`. Дополнительно в процессе тики не
  накладываются: следующий планируется через `setTimeout` только после
  завершения текущего, а не через `setInterval`.
- **`is_running` снимается только после завершения проверки** (успех,
  ошибка или таймаут). Проверка, выполняющаяся дольше своего интервала,
  физически не может быть захвачена второй раз.
- **Пропущенные слоты не догоняются.** `next_run_at` — ближайший слот
  строго в будущем на сетке «запланированное время + k·интервал». Если
  проверка шла 45 с при интервале 30 с, следующая пойдёт через 60 с от
  предыдущей, а не сразу же. Две причины: не устраивать залп запросов по
  сайту, который и так тормозит; после простоя backend не делать пачку
  догоняющих проверок (важно для сценария «после перезапуска — пробел, а не
  ложное падение», этап 11).
- **Сетка привязана к запланированному времени, а не к фактическому
  старту.** Иначе задержка тика (до 1 с) накапливалась бы: за час проверка
  с интервалом 30 с «уезжала» бы на десятки секунд. Ручной запуск начинает
  сетку заново от момента запуска.
- **Тик 1 с.** Этого достаточно при минимальном интервале 30 с: задержка
  старта до 1 с, нагрузка — один индексируемый запрос в секунду. Меньший
  тик дал бы точность, которая здесь не нужна.
- **Каждая проверка — независимая асинхронная задача** (fire-and-forget из
  тика) со своим `AbortSignal.timeout`. Медленная проверка держит только свой
  сокет. Верхняя граница одновременно выполняющихся — 500, заведомо больше
  50 из ТЗ, это защита от исчерпания сокетов, а не троттлинг.
- **Зависший lock.** При старте процесс снимает все `is_running`: backend
  один, значит, это lock умершего процесса. На случай потерянной задачи
  без рестарта lock старше `timeout + 60 с` считается брошенным и
  перехватывается. Ограничение: предположение об одном экземпляре backend.
  Горизонтальное масштабирование потребовало бы heartbeat владельца lock.
- **Остановка по SIGTERM:** новые проверки не берутся, выполняющиеся
  прерываются, их lock снимается, результат не записывается. Прерванная
  проверка — это «нет данных», а не падение.
- **Время ответа включает чтение тела** (не больше 1 МБ — защита памяти):
  столько ждёт посетитель, и тело всё равно нужно для проверки подстроки.
  Редиректы проходятся (`redirect: follow`), ожидаемый код сравнивается с
  кодом финального ответа.
- **Время — часы процесса backend** передаются в SQL параметром, а не
  `now()` БД. И захват, и расчёт `next_run_at` пользуются одним источником
  времени.

**Найдено и исправлено в ходе этапа.**
- **SIGTERM не доходил до node.** В Dockerfile backend запускался через
  `sh -c "migrate && node …"`: PID 1 был `sh`, и сигнал от
  `docker compose restart` до node не доходил. Корректная остановка не
  срабатывала никогда, выручал только сброс lock при старте. Исправлено на
  `exec node`, проверено: `shutting down → aborted: 2 → scheduler stopped`.
- **Задержка старта 4,2 ч у первых запусков — реальный простой, а не
  ошибка.** Демо-проверки созданы на этапе 2 (08:34 UTC) и ни разу не
  запускались: планировщика ещё не было, а стек был остановлен между
  этапами. Первый запуск после старта планировщика (12:48 UTC) честно
  показал задержку 4 ч 14 мин. Сначала я ошибочно списал это на отставание
  часов Docker VM и так и записал в этот файл. Перепроверил по NTP: часы
  верные, запись исправлена. Заодно это реальная проверка пропуска слотов
  после простоя: `next_run_at` встал ровно на сетку
  `08:34:29.995 + k·30 с`, пачки догоняющих запусков не было.

**Как проверено.**
- **Наложение:** проверка `/slow?ms=45000` с интервалом 30 с по журналу
  эмулятора приходит раз в 60 с (12:49:36, 12:50:37), параллельных
  запросов нет.
- **Гонка:** 20 параллельных ручных запусков 5-секундной проверки — ровно
  один 202, остальные 409, эмулятор получил один запрос.
- **Задержка старта** остальных проверок — 0,1–1 с, пока рядом висит
  45-секундная.
- **Тексты ошибок:** `timeout after 2000 ms`, `body does not contain "welcome"`,
  `ENOTFOUND`.
- **Юнит-тесты `computeNextRunAt`:** 5 из 5.

## 2026-09-18 19:34 — Этап 5: определение инцидентов и хранение истории

**Сделано.** Таблицы `check_results` и `incidents`. Каждый результат
проверки пишется в историю. Статус проверки (`unknown/up/down`) меняется по
порогам, инциденты открываются и закрываются с посчитанной длительностью.
API: `GET /api/checks/:id/results`, `GET /api/incidents`. Frontend: карточка
проверки (последние результаты и её инциденты) и общий журнал инцидентов.

**Решения:**

- **Порог падения — 2 неудачи подряд, восстановления — 1 успех.** Порог 2
  отсекает одиночный сбой: потерянный пакет, разовый таймаут, рестарт
  сайта за секунду. При этом при интервале 30 с падение фиксируется не
  позже чем за ~1 минуту. Порог 3 давал бы до 1,5 минут задержки, а
  одиночный ложный сигнал и так отсечён. Восстановлению достаточно одного
  успеха: успешный ответ — положительное доказательство работы, а ложные
  успехи на практике не встречаются. Асимметрия осознанная: ложное
  «упало» стоит письма и тревоги, ложное «поднялось» почти невозможно.
  Пороги — константы в `monitor/transitions.ts`.
- **Начало инцидента — время первой неудачи серии, а не момент
  срабатывания порога.** Сайт перестал отвечать именно тогда. Для этого
  добавлено поле `checks.failing_since`. Отсюда же считается «падение
  длится» на панели.
- **Новая проверка:** первый успех — сразу `up` (`became_up`, не инцидент
  и, на этапе 7, не письмо «восстановился»). Если проверка ни разу не
  работала, после 2 неудач она сразу `down` с инцидентом: для владельца
  это такое же падение.
- **Правила переходов — чистая функция `evaluate(state, ok, at)`** без БД.
  Покрыта юнит-тестами: одиночный сбой, порог, начало с первой неудачи,
  ровно один `went_down` на серию неудач, восстановление и новый инцидент.
- **Всё в одной транзакции:** результат, счётчики, статус, открытие или
  закрытие инцидента, `next_run_at` и снятие lock. Не бывает состояния
  «статус down, а инцидента нет» или «lock снят, а результат не записан».
  `applyResult` возвращает, какой переход произошёл. Это точка
  расширения для SSE (этап 6) и писем (этап 7).
- **Не больше одного открытого инцидента на проверку — гарантия БД**:
  частичный уникальный индекс `ON incidents(check_id) WHERE ended_at IS NULL`
  (Prisma такие индексы не описывает, поэтому он дописан в миграцию
  руками). Вставка — `ON CONFLICT DO NOTHING`: если открытый инцидент
  почему-то уже есть, сохраняется он, транзакция не падает.
- **В историю пишется время отправки запроса** (`checked_at` = старт
  проверки), а не время ответа. Для таймаута в 5 с сайт был недоступен в
  момент запроса.
- **Пробел после простоя получается сам.** Пропущенные слоты не
  исполняются (этап 4), значит, за время простоя в `check_results` просто
  нет строк. Неудача пишется только по реальной неудачной проверке, поэтому
  простой backend не может породить ложный инцидент. Счётчик неудач
  переживает рестарт — и это правильно: две настоящие неудачи подряд по
  разные стороны рестарта — это падение.
- **Индекс `check_results(check_id, checked_at)`** обслуживает все запросы
  истории: «проверка + диапазон времени». Хранение сырых результатов без
  ограничения срока — осознанное упрощение. Агрегаты и замер — этап 10.
- **Удаление проверки удаляет её историю и инциденты** (`ON DELETE CASCADE`).
  UI честно предупреждает об этом в подтверждении.

**Найдено и исправлено до коммита.** Первая версия `applyResult`
записывала обратно всю строку проверки, прочитанную в начале транзакции.
Правка проверки, пока она выполняется, откатилась бы к старым значениям.
Теперь пишутся только поля мониторинга. Проверено: переименование во время
3-секундной проверки сохранилось.

**Как проверено.**

## 2026-09-18 20:46 — Этап 6: live-обновления панели через SSE

**Сделано.** Внутрипроцессная шина событий, в которую публикуют
планировщик (захват проверки, результат, смена статуса, инциденты, статус
группы) и CRUD-роуты. `GET /api/stream` (только для admin) отдаёт события
как SSE. Клиент: хук `useLiveStream` точечно правит кэш TanStack Query,
индикатор соединения в шапке. Временный опрос раз в 5 с с этапов 4–5 удалён.

**Решения:**

- **SSE, а не WebSocket.** Поток однонаправленный: после подключения
  клиенту нечего отправлять серверу, все действия идут обычными
  REST-запросами. SSE — это обычный HTTP-ответ, поэтому он проходит через
  тот же nginx-прокси, авторизуется той же cookie и тем же `preHandler`, что
  и API, и не требует отдельного протокола и библиотеки на обеих сторонах.
  Автоматическое переподключение встроено в `EventSource`. Тот же механизм
  без авторизации будет у публичной страницы (этап 9). WebSocket дал бы
  двунаправленность, которая здесь не нужна, ценой ручного
  переподключения, heartbeat-протокола и отдельной авторизации апгрейда.
- **События — патчи кэша, а не сигнал «перечитай всё».** При 50 проверках
  раз в 30 с это ~3–5 событий в секунду. Если бы каждое вызывало
  перезапрос списка в каждой вкладке, нагрузка на backend росла бы
  пропорционально числу вкладок. `check.upsert` несёт либо полную
  проверку, либо патч (`{id, isRunning: true}` при захвате), клиент мёржит
  его в список и карточку. Редкие события — CRUD групп, открытие и
  закрытие инцидента — делают инвалидацию: они редкие, а собирать патч
  для них сложнее.
- **Статус группы считает сервер и присылает событием `group.status`**,
  только когда у проверки этой группы сменился статус. Правило «группа
  down, если упала хотя бы одна активная проверка» остаётся в одном месте
  (`monitor/groupStatus.ts`), а не дублируется на клиенте.
- **Пропущенные события не воспроизводятся (нет `Last-Event-ID`/буфера).**
  Вместо этого при каждом (пере)подключении клиент перечитывает всё
  (`invalidateQueries()`). Источник истины — БД, повтор событий дал бы ту
  же картину, но потребовал бы хранить журнал событий на сервере.
- **Две вкладки = два независимых `EventSource`**, сервер рассылает каждое
  событие всем подписчикам шины. Синхронизация вкладок между собой
  (BroadcastChannel) не нужна: каждая получает всё от сервера.
- **Шина — `EventEmitter` в процессе**, без Redis pub/sub: backend один
  (то же ограничение, что у планировщика, см. этап 4).
- **Надёжность потока:** heartbeat-комментарий раз в 15 с (не даёт прокси и
  NAT закрыть «молчащее» соединение); `retry: 3000`; медленный клиент с
  буфером больше 1 МБ отключается, а не копит память; при SIGTERM все
  потоки закрываются явно. Иначе `app.close()` ждал бы долгоживущие
  соединения. `X-Accel-Buffering: no` в дополнение к
  `proxy_buffering off` в nginx.
- **Ошибка публикации не считается ошибкой проверки:** результат к этому
  моменту уже закоммичен, теряется только свежесть UI до следующего
  события или переподключения.
- **Известное ограничение:** браузер держит не больше 6 HTTP/1.1-соединений
  на origin, и каждая вкладка занимает одно под SSE. При 6+ открытых
  вкладках панели обычные запросы начнут ждать. Решения — HTTP/2 (в nginx
  требует TLS) или один поток на все вкладки через SharedWorker. Для
  локального тестового стенда с двумя вкладками из ТЗ не делалось,
  записано в README.

**Как проверено.**
- **Сырой поток через nginx:** события приходят в момент возникновения
  (результат 3-секундной проверки — через 3 с после её старта), без
  пачек. Без cookie — 401.
- **Две вкладки в headless Chrome,** изменения через API: создание,
  первый запуск, падение (2 неудачи), восстановление, пауза, удаление —
  все 6 шагов видны в **обеих** вкладках за 3–32 мс, без перезагрузки
  страницы (метка `window.__noReload` сохранилась). На сервере ровно
  2 SSE-клиента.
- **`docker compose restart backend` с открытым потоком:** остановка < 1 с,
  поток закрыт штатно. Вкладка: `live` → «переподключение…» через 0,2 с →
  снова `live` через 3,2 с, данные на экране не пропадали.

## 2026-09-18 21:06 — Этап 7: письма через MailDev, только при смене состояния

**Сделано.** Письмо `[DOWN]` при открытии инцидента и `[UP]` при его
закрытии, на адреса группы проверки (для проверок без группы — на
`DEFAULT_ALERT_EMAILS` из `.env`). Состояние отправки хранится в инциденте
и показывается в журнале (колонка «Письма»). Отправка через nodemailer в
MailDev.

**Решения:**

- **«Только при смене состояния» обеспечивается инцидентом, а не
  флагами в памяти.** Писем ровно два на инцидент: DOWN и UP. Инцидент
  открывается один раз на серию неудач (этап 5, плюс гарантия БД «один
  открытый инцидент на проверку»), поэтому сколько бы неудачных проверок
  ни было между падением и восстановлением, повода для третьего письма
  нет по построению.
- **Письма отправляет сверщик по состоянию БД, а не обработчик события
  перехода.** Сверщик (`AlertDispatcher`) запускается сразу после любого
  перехода статуса и раз в 15 с. Он ищет инциденты, где письмо положено, но
  не отправлено (`down_alert_at IS NULL`; для UP — инцидент закрыт, DOWN
  разобран, `up_alert_at IS NULL`). Одним механизмом закрываются:
  повтор при недоступном SMTP; отправка после краша backend между
  фиксацией падения и письмом (новый процесс найдёт неотправленное); и на
  этапе 8 — «окно обслуживания закончилось, а сайт всё ещё лежит → письмо»:
  сверщик просто перестанет пропускать этот инцидент.
- **Защита от двойной отправки** — claim условным
  `UPDATE … SET down_alert_status = 'sending' WHERE id = ? AND down_alert_at IS NULL`
  перед SMTP-вызовом. Немедленный запуск и плановый не отправят одно
  письмо дважды. Внутри процесса запуски сверщика не накладываются (флаг
  `running` + повторный прогон, если был запрошен во время текущего).
- **Семантика доставки — «не больше одного раза», с одним исключением.**
  Ошибка SMTP снимает claim, и письмо повторяется на следующей сверке.
  Если процесс умер *во время* SMTP-вызова, claim `sending` старше 2 минут
  снимается, и письмо может уйти второй раз. Выбрано осознанно: для
  оповещения о падении дубль лучше потери. Окно — длительность одного
  SMTP-вызова, ограниченная таймаутами (5 с на соединение).
- **Порядок гарантирован:** UP отправляется только после того, как DOWN
  разобран. Если DOWN так и не ушёл (нет адресатов), UP помечается
  `skipped`: письмо «восстановился» без письма «упал» только сбивает с
  толку. Если сайт восстановился, пока DOWN не удавалось отправить (SMTP
  лежал), уйдут оба письма, с опозданием: инцидент реально был, и владелец
  должен о нём узнать.
- **Адресаты берутся на момент отправки** из текущей группы проверки. Нет
  адресатов — статус `no_recipients`, ничего не отправляется, в журнале это
  видно. `DEFAULT_ALERT_EMAILS` добавлен, потому что без него проверкам без
  группы вообще некуда слать, а группа в ТЗ необязательна.
- **nodemailer 8, а не последний 10.x.** Самые свежие типы
  (`@types/nodemailer` 8.0.2) описывают 8.x. API отправки через SMTP
  между мажорами для нас не менялся, а расхождение типов с библиотекой —
  лишний риск. Таймауты SMTP сокращены (5/5/10 с): по умолчанию nodemailer
  ждёт минутами, и мёртвый SMTP надолго держал бы сверщик.
- **Время в письмах** — в зоне `DISPLAY_TIMEZONE` (по умолчанию UTC), зона
  подписана рядом со временем. Сервер в Docker живёт в UTC, а читателю
  письма нужна однозначность.
- **Письмо `[UP]` не шлётся для `unknown → up`** (первые данные новой
  проверки), только для настоящего восстановления после инцидента.

**Как проверено** (MailDev API `GET /email`, управляемая цель эмулятора).
- **Основной сценарий:** первый успех — 0 писем; одна неудача — 0; вторая
  — 1 (`[DOWN]`); ещё три неудачи — по-прежнему 1; успех — 2 (`[UP]`,
  длительность 4 с); одиночный сбой потом — по-прежнему 2. Письмо ушло
  обоим адресатам группы.
- **При старте backend** сверщик нашёл открытый инцидент прошлого этапа
  без письма и отправил DOWN.
- **Проверка без группы** — письмо на `DEFAULT_ALERT_EMAILS`. Группа без
  адресов — `no_recipients`, писем 0.
- **MailDev остановлен на время падения:** отправка упала через 5 с
  (`Connection timeout`), claim снят, после запуска MailDev письмо
  доставлено ближайшей сверкой — ровно одно.
- **Ошибка в первом тесте SMTP.** В первой попытке MailDev поднялся
  раньше, чем истёк таймаут соединения, и зависшая отправка просто
  прошла. Путь повтора не был проверен, тест переделан: MailDev
  выключен дольше таймаута.

## 2026-09-19 01:06 — Этап 8: окна обслуживания

**Сделано.** Таблица `maintenance_windows` (окно для одной проверки или для
группы), API `/api/maintenance` (список текущих и прошедших окон,
создание, «завершить сейчас», удаление), учёт окон в сверщике писем.
Страница «Обслуживание» и метки «обслуживание до ЧЧ:ММ» на панели.

**Решения:**

- **Окно влияет только на письма.** Проверки в окне выполняются как
  обычно, статусы, история и инциденты фиксируются: этого требует ТЗ, и
  так после окна видно, что происходило во время работ.
- **Письма во время окна откладываются, а не отбрасываются.** Сверщик из
  этапа 7 пропускает инцидент, пока его проверка (напрямую или через
  группу) в активном окне. Отсюда три случая:
  - **сайт упал во время окна, окно кончилось, а сайт всё ещё лежит** —
    инцидент открыт и без письма, ближайшая сверка (≤ 15 с) отправляет
    DOWN с примечанием «падение началось во время обслуживания»;
  - **сайт упал и поднялся внутри окна** — DOWN помечается `suppressed`,
    UP — `skipped`, писем нет: простой был плановым;
  - **сайт упал до окна (DOWN ушёл), а поднялся во время окна** — UP
    отложен до конца окна, иначе владелец остался бы с одним письмом
    «упал».
  Критерий «целиком внутри окна» — время *восстановления* попадает в
  окно. Если сайт поднялся уже после окна, DOWN уйдёт, даже с опозданием.
- **Ровно одна цель у окна — ограничение БД** (`CHECK ((check_id IS NULL) <> (group_id IS NULL))`)
  плюс `ends_at > starts_at`. Отдельная таблица на проверки и на группы
  дала бы два почти одинаковых API.
- **«Начать сейчас» — по часам сервера.** API принимает `startsAt`
  необязательно (по умолчанию — серверное «сейчас») и длительность
  `durationMinutes` вместо `endsAt`. В режиме «Начать сейчас» форма
  отправляет только длительность, и часы браузера вообще не участвуют.
  Нашёл это на тестах: часы Docker Desktop VM после сна Mac отставали от
  хоста на ~15 минут. Окно, созданное с началом «сейчас» по часам
  клиента, для backend начиналось через 15 минут, и письма во время
  «работ» уходили. Та же проблема была бы у браузера с неточными часами.
- **Клиент считает «сейчас» по часам сервера:** сдвиг берётся из
  SSE-события `hello`. Через него идут «падение длится», метки
  обслуживания и остаток окна. Раньше они считались от часов браузера.
- **Метки обслуживания на панели считает клиент** по списку текущих окон
  и серверному «сейчас». Они появляются и исчезают точно на границах окна
  без события от сервера (на границах окна сервер ничего не делает).
  Изменения самих окон приходят событием `maintenance.changed`.
- **«Завершить сейчас» для ещё не начавшегося окна** его удаляет: иначе
  получилось бы окно с концом раньше начала.
- **Удаление проверки или группы удаляет её окна** (`ON DELETE CASCADE`).

**Как проверено:** сценарии через API, MailDev и управляемую цель эмулятора
(проверка на паузе, ручные запуски).
- **Валидация:** окно без окончания и длительности, окно сразу с
  окончанием и длительностью, окно с двумя целями — 400. Вставка в БД без
  цели отклоняется CHECK-ограничением.
- **S1, упал во время окна, окно закончилось, а сайт лежит:** в окне статус
  `down`, инцидент открыт, писем 0 (ждал дольше одной сверки). После
  окончания окна DOWN пришёл через 2 с с примечанием про обслуживание,
  затем UP после восстановления.
- **S2, упал и поднялся внутри окна:** `suppressed`/`skipped`, писем 0, в том
  числе через 17 с после конца окна.
- **S3, DOWN ушёл до окна, поднялся в окне:** UP отложен и ушёл через 14 с
  после конца окна (ближайшая сверка).
- **S4, окно на другой группе** письма этой проверки не задерживает.
- **UI (headless Chrome, без перезагрузки):** метки «обслуживание до …» у
  группы и трёх её проверок появились через 51 мс после создания окна
  через API и исчезли через 44 мс после «завершить сейчас».

**Найдено по ходу этапа:**
- **Часы Docker Desktop VM** на этой машине дважды отставали от хоста на
  ~15 минут (922 и 925 с) и потом рывком досинхронизировались: после сна
  Mac, во время тестов. Из-за этого первая версия (окно «с сейчас» по
  часам клиента) провалила сценарии, что и привело к решению «начало и
  длительность по часам сервера» выше. Вторая версия проходит сценарии и
  при отставании в 15 минут. Для тестов часы выравнивались через
  `docker run --rm --privileged postgres:16-alpine hwclock -s`.
- **Известное ограничение:** если часы сервера прыгнут *назад*, уже
  посчитанные `next_run_at` окажутся в будущем, и проверки будут стоять
  до выравнивания часов. На сервере с NTP так не бывает, а в Docker
  Desktop после сна — бывает. Защита (перепланировать, если `next_run_at`
  дальше, чем «сейчас + интервал») — в планах, см. README.
- **Ошибки моих тестовых скриптов (не кода):** действия с пустым телом
  отправлялись с `content-type: application/json`, и Fastify отвечал 400;
  при повторном запуске не был остановлен предыдущий фоновый прогон, и
  два скрипта мешали друг другу. Исправлено, результаты выше — из
  одного чистого прогона.

## 2026-09-19 04:49 — Доработка UI, шаг 2: сводка для панели (backend)

**Сделано.** `GET /api/dashboard/summary` → `{ total, up, down, paused,
unknown, uptime24h, computedAt }`. Та же сводка приходит SSE-событием
`summary` в существующем потоке `/api/stream`.

**Решения:**

- **Счётчики — по правилу статуса группы.** Проверка на паузе не
  «работает» и не «упала», а считается отдельно (`paused`). `unknown` —
  активные проверки без вердикта (новые или ещё не набрали порог).
- **Аптайм за 24 ч — среднее аптаймов проверок, а не доля успешных
  результатов по всем проверкам сразу.** Иначе проверка с интервалом 30 с
  весила бы в 120 раз больше часовой. Проверки без результатов за сутки в
  среднее не входят; если результатов нет совсем — `null` («—» в UI).
- **Запрос через коррелированный подзапрос по каждой проверке:** так
  используется индекс `(check_id, checked_at)`. Фильтр только по
  `checked_at` этот индекс использовать не может и читал бы все
  результаты. При переходе к агрегатам (этап 10) запрос можно перевести
  на них.
- **Живое обновление — подписчик на внутренней шине, а не вызовы из
  планировщика.** Планировщик, инциденты и SSE-транспорт не менялись:
  модуль `dashboard/summary.ts` слушает `check.upsert`, `check.deleted`,
  `check.result` и публикует новое событие `summary`.
- **Пересчёт не чаще раза в 3 с.** Результаты приходят непрерывно, а
  сводка — это запрос по всем проверкам. Первое изменение после паузы
  публикуется сразу, следующие в пределах 3 с объединяются в один пересчёт.
  Если открытых SSE-соединений нет, сводка не считается вовсе: панель при
  подключении сама запрашивает её через GET.
- **`/api/stream/clients` теперь считает открытые SSE-соединения, а не
  подписчиков шины.** У шины появился второй, внутренний подписчик, и
  старый счётчик завышал бы число клиентов на единицу.

**Как проверено:** значение `uptime24h` (79.18) совпало с ручным
расчётом по `check_results` в psql; событие `summary` приходит в
`/api/stream` после результатов проверок.

## 2026-09-19 15:55 — Этап 9: публичная страница статуса

**Перед этапом** повторно прогнал сценарии этапа 8 (окна обслуживания)
скриптом через API и MailDev: S1–S4, 11 из 11 проверок, в письме S1 есть
примечание про обслуживание.

**Сделано.** Страница `/status` без входа (то же SPA, вне админской
оболочки), `GET /api/public/status` и SSE-поток `GET /api/public/stream`.
Показываются только проверки с `is_public = true`, сгруппированные по
группам, общий баннер («Все сервисы работают» / «Недоступно сервисов: N» /
«Идут плановые работы»), статус, длительность падения, аптайм за 24 ч и
метка «плановые работы до …». В шапке админки — ссылка «Публичная
страница ↗».

**Решения:**

- **Белый список полей, а не «проверка минус секреты».** Наружу уходят
  только `id, name, status, since, lastCheckedAt, group, uptime24h` и
  интервалы окон обслуживания (`public/view.ts`). Не отдаются: URL (может
  указывать на внутренние хосты), тексты ошибок и HTTP-коды, время ответа,
  адреса для писем, заметки окон обслуживания. Новое поле в модели не
  утечёт само: его нужно явно добавить в список.
- **Отдельный поток `/api/public/stream` с фильтром на той же шине.**
  Используется `openEventStream` с функцией `toPublicEvent`:
  - полная строка публичной проверки превращается в событие `check` с
    полями из белого списка;
  - проверка, ставшая приватной, превращается в `check.removed`: её
    данные не уходят, а страница убирает строку сразу;
  - частичные патчи планировщика (`isRunning`) отбрасываются: в них нет
    `isPublic`, а посетителю они не нужны;
  - `check.result`, `incident.*`, `summary` отбрасываются;
  - `group.status` тоже отбрасывается, потому что он учитывает приватные
    проверки группы;
  - изменения групп и окон превращаются в `changed`, и страница
    перезапрашивает список.

  Этот фильтр покрыт unit-тестами (`public/view.test.ts`).
  `openEventStream` теперь принимает фильтр, который возвращает любое
  событие `{ type, data }`, а не только админское; остальной транспорт
  не менялся.
- **Статус группы на публичной странице считается только по её публичным
  проверкам** (на клиенте, тем же правилом, что и на бэкенде). Иначе
  упавшая приватная проверка окрашивала бы группу в красный без видимой
  причины.
- **Проверка на паузе показывается как «мониторинг приостановлен»,** а не
  последним статусом. Иначе посетитель видел бы устаревшее «работает» или
  «недоступен».
- **Падение во время окна обслуживания не считается в баннере как
  «недоступно»:** баннер показывает «Идут плановые работы», у строки
  остаются оба бейджа.
- **Аптайм за 24 ч на публичной странице — по проверке**, одним запросом
  `GROUP BY check_id` по публичным проверкам (`check_id = ANY(...)`
  использует индекс). По каждому результату в поток не отправляется:
  страница перезапрашивает список раз в минуту. Статусы при этом приходят
  живьём.
- **Хук `useLiveStream` принимает набор обработчиков**, по умолчанию
  админский. Публичная страница передаёт свой: она пишет в свой ключ
  кэша и не знает об админских запросах.

**Известные ограничения** (попадут в README):
- Публичный поток открыт без входа, и число соединений не ограничено.
  Для реального развёртывания нужен лимит на IP на прокси.
- Сводка админки (`summary`) пересчитывается и тогда, когда открыты
  только публичные страницы. Это один запрос раз в 3 с, на результат не
  влияет.

**Как проверено:**
- `/api/public/status` без cookie отдаёт 3 публичные проверки из 5, в
  ответе нет URL и служебных полей; `/api/checks` без cookie → 401.
- **Живой сценарий** (headless Chrome, страница открыта без входа, действия
  через админский API):
  - публичная проверка создана → строка появилась через 70 мс;
  - два неудачных запуска → «недоступен», баннер «Недоступно сервисов: 2»
    через 40 мс;
  - окно обслуживания → метка «плановые работы до …», баннер снова
    считает недоступным один сервис;
  - снят флаг «публичная» → строка исчезла через 15 мс;
  - заметка окна на страницу не попала.
- Ширина 390 px и тёмная тема — вёрстка в порядке. Админская панель после
  правки хука — live, 5 строк, сводка обновляется.

## 2026-09-19 21:11 — Этап 10: графики истории и почасовая свёртка

**Сделано.** На странице проверки — блок «История» с переключателем
«Сутки / Неделя / Месяц»:
- карточки: аптайм, среднее время ответа, число инцидентов, простой;
- график «Неудачные проверки, %» (столбики);
- график «Среднее время ответа, мс» (линия с заливкой);
- общий для обоих графиков перекрёстный курсор с подсказкой (мышь и
  клавиатура: стрелки);
- таблица с теми же данными.

API: `GET /api/checks/:id/stats?range=day|week|month`. Новая таблица
`check_results_hourly` — почасовая свёртка истории.

**Замер, на котором основано решение** (`scripts/bench/history-rollup.sql`,
в отдельной схеме, приложение не затрагивается). 50 проверок × 30 дней ×
каждые 30 с = 4,32 млн строк, 504 МБ; строки разных проверок перемешаны
по страницам, как в жизни. Запрос «месяц одной проверки, корзины по 6 ч»:

| Источник | Холодный кэш | Прогретый | Прочитано страниц |
|---|---|---|---|
| сырые `check_results` | 261 мс | 74–76 мс | 36 335 (≈ вся таблица) |
| почасовая свёртка | 2,2 мс | 0,5 мс | 305 |

Неделя по сырым данным — 6–7 мс, сутки — около 1 мс (2 880 строк).

**Решения:**

- **Почасовая свёртка для недели и месяца, сырые данные — для суток.**
  Индекс `(check_id, checked_at)` находит строки проверки быстро, но
  каждая строка лежит на своей странице вперемешку с остальными
  проверками. Месяц одной проверки читает почти всю таблицу, и с ростом
  числа проверок станет только хуже. Свёртка — 720 строк на проверку в
  месяц, 3,7 МБ на весь объём против 504 МБ. Для суток нужны 15-минутные
  корзины, которых в свёртке нет, а сырой запрос там и так ~1 мс.
- **Свёртка пополняется в той же транзакции, что и запись результата**
  (`INSERT … ON CONFLICT DO UPDATE` в `applyResult`), а не фоновой
  задачей. Так она не расходится с сырыми данными ни на секунду: не нужны
  «догоняющий» процесс, учёт уже свёрнутых часов и склейка «свёртка +
  хвост из сырых». Конкуренции за строку нет: строку часа обновляет
  только своя проверка, а её запуски не пересекаются (этап 4).
  Цена — одна дополнительная запись на результат. Отдельно я её не мерил;
  это UPSERT по первичному ключу в уже открытой транзакции.
- **Миграция заполняет свёртку из уже накопленной истории**, сверено: сумма
  `total` по свёртке равна числу строк `check_results` (1406 = 1406), в
  том числе с результатами, записанными после миграции.
- **В свёртке хранятся суммы, а не средние:** `total`, `failures`,
  `sum_ms_ok`, `max_ms_ok`. Суммы складываются в корзины любого размера,
  средние — нет. Перцентили (p95) из свёртки не получить. Поэтому на
  графике среднее и максимум, без p95.
- **Время ответа — только по успешным проверкам.** Таймаут на 5 с
  говорит о недоступности, а не о скорости. Его учитывает график неудач.
- **Доступность показана высотой, а не цветом.** Сначала планировалась
  полоса «зелёный / жёлтый / красный». Валидатор палитры показал, что
  зелёный и красный неразличимы при дейтеранопии (ΔE 4–5 при нужных ≥ 8).
  Поэтому столбик одного цвета с высотой = доля неудачных проверок.
  Одна неудача всё равно видна: минимальная высота 3 px. Цвета графиков
  (`--chart-line`, `--chart-bad`) проверены валидатором для светлой и
  тёмной темы: для тёмной темы взяты более тёмные тона, чем у бейджей.
- **Пустые корзины — «нет данных», а не 0 % и не 100 %:** проверка на
  паузе или backend не работал. На графике это серая черта у оси, линия
  времени ответа в этом месте разрывается. API возвращает все корзины,
  включая пустые (`generate_series` + `LEFT JOIN`).
- **«Простой» считается по инцидентам, аптайм — по результатам.** Одна
  неудача ниже порога — не падение, поэтому простой — сумма пересечений
  инцидентов с периодом. Аптайм — доля успешных проверок, как на
  дашборде.
- **Сетка корзин привязана к UTC, подписи оси — к местному времени.**
  Корзины выровнены по фиксированному началу отсчёта и не «ездят» между
  запросами. Подписи ставятся там, где у зрителя начинаются сутки, три
  часа и т. п. На узком экране подписи прореживаются. Ограничение: в
  поясах со сдвигом не на целый час (Индия, +5:30) часовые корзины не
  совпадают с местными часами.
- **SVG вручную, без библиотеки графиков.** Два маленьких графика с одной
  серией: библиотека добавила бы сотни килобайт и зависимость ради того,
  что укладывается в один компонент.
- **При смене периода старые данные остаются на экране** (полупрозрачно),
  пока грузятся новые, без мигания. Данные за сутки обновляются раз в
  30 с, за неделю и месяц — раз в 5 минут.
- **Аптайм за 24 ч в сводке дашборда и на публичной странице теперь тоже
  из свёртки** (было отмечено на шаге 2 доработки UI). Это 24–25 строк на
  проверку вместо до 2 880. Окно — последние 24 полных часа плюс текущий,
  то есть от 24 до 25 часов. Разница с точными 24 ч для этой метрики
  несущественна.

**Как проверено:**
- unit-тесты сетки корзин;
- `prisma migrate diff` между базой и схемой — «No difference detected»;
- 404 для несуществующей проверки;
- временная проверка на паузе с месяцем истории из замера (2-часовое
  падение 10 дней назад, 6-часовой пропуск 3 дня назад, медленные ночные
  часы). Пустые часы в ответе API совпали с вырезанным пропуском

  1280 и 390 px, светлая и тёмная тема. Подсказка и перемещение
  стрелками работают. После проверки временная проверка удалена вместе с

**Ошибка в тестовых данных (не в коде):** инцидент для временной проверки я
вставил со статусом писем `skipped`, но без `down_alert_at`. Сверщик

не ушло. Сверщик ведёт себя правильно: инцидент без отметки времени
письма для него не обработан.

## 2026-09-20 15:40 — Кнопка ручного запуска: понятное название и видимый результат

**Найдено при приёмке этапа 10:** кнопка «Запустить» выглядела неработающей.

**Разобрался.** Кнопка работала: `POST /api/checks/:id/run` выполняет пробу
немедленно, пишет результат в историю и переносит следующий запуск
(проверено по API: проба 1 мс, `lastCheckedAt` обновился, `nextRunAt`
сдвинулся на интервал от текущего момента). Проблема была в обратной
связи: проба занимает единицы миллисекунд, метка «идёт проверка…» мелькает
и исчезает, а видимое изменение — только «последняя проверка: 0с назад».

**Сделано.**
- Кнопка названа «Проверить сейчас», в подсказке сказано, что проверка
  выполнится немедленно, попадёт в историю и отсчёт интервала начнётся
  заново.
- После нажатия в строке на 8 секунд появляется результат именно этого
  запуска: «проверено: успех, 9 мс» или «проверено: неудача — expected
  HTTP 200, got 500».

**Решения:**

- **Показывается результат пробы, а не факт «запрос принят».** Одна
  неудача ниже порога не меняет статус проверки, и без этого текста
  пользователь, нажавший кнопку на сломанном сайте, видел бы «успешное»
  молчание.
- **Результат берётся из уже существующего события `check.result`**, оно
  дополнительно кладётся в кэш по ключу «последний результат проверки».
  Эндпоинт остался асинхронным (202): ждать ответа нельзя, проверка может
  длиться до таймаута.
- **Сравнение по времени результата:** показывается только результат,
  полученный после нажатия, чтобы плановая проба не выдавалась за ручную.

## 2026-09-20 16:47 — Этап 11: скрипт доказуемости

**Сделано.** `scripts/verify.mjs` — один запуск проверяет каждый пункт
«Ожидаемого поведения» из задания на живой системе и печатает PASS/FAIL.
Полный прогон: 10 из 10, около 4 минут. Раздел «Как проверить, что всё
работает» в README заполнен.

**Решения:**

- **Сценарии повторяют формулировки задания, один к одному.** Десять
  сценариев: `crud`, `live`, `threshold`, `alerts`, `maintenance`,
  `overlap`, `load`, `month`, `public`, `restart`. Так проверяющий видит
  не «тесты прошли», а ровно те утверждения, которые ему обещали.
- **Скрипт работает по сети, как обычный клиент:** HTTP-API панели,
  публичный API без входа, SSE-потоки, управляющие ручки эмулятора,
  HTTP-API MailDev. В БД он лезет только чтобы засеять историю для
  сценария `month` (через `docker compose exec psql`) и в `restart`
  останавливает контейнер backend.
- **Без зависимостей и без фреймворка тестов.** Нужен только Node 22+ на
  хосте (уже в пререквизитах). Свой мини-раннер печатает по каждому
  сценарию замеры и список выполненных утверждений — это и есть отчёт.
- **Проверки скрипта живут отдельно от пользовательских.** Имена
  `verify-<время>-…`, за собой всё удаляется, письма не очищаются, а
  фильтруются по имени проверки. Поэтому скрипт можно запускать на стенде
  с уже заведёнными проверками.
- **Детерминированность через паузу и ручные запуски.** Там, где важна
  последовательность (порог, письма, окно обслуживания), проверка стоит на
  паузе и каждый шаг — один ручной запуск. Где важна именно работа
  планировщика (`live`, `overlap`, `load`, `restart`), проверки идут сами.
- **Независимые доказательства, а не самоотчёт backend.** Параллельность и
  регулярность опроса считаются по журналу обращений эмулятора
  (`/control/hits`): в `overlap` — ровно один запрос за 40 секунд,
  в `load` — максимальный интервал между опросами одной цели 30,1 с при
  заданных 30 с. Письма берутся из MailDev, а не из статусов в БД.
- **`month` засевает 864 000 результатов** (10 проверок × 30 дней × 30 с)
  и меряет ответ API: месяц 4 мс, неделя 2 мс, сутки 3 мс. Без объёма
  утверждение «открывается быстро» ничего не значит.
- **Флаги `--quick` и `--only=`** — полный прогон идёт 4 минуты, из них
  больше половины ожидания (45 с простоя в `restart`, 95 с нагрузки,
  сверки писем по 20 с).

**Найдено по ходу:**
- **Ошибки в самом скрипте, не в продукте:** `runOnce` возвращал результат
  ожидания, а не проверку; в `live` ловилось первое событие пробы
  («началась»), а не событие с результатом; в `load` в журнал обращений
  попадала существующая проверка стенда на `/ok`.
- **Публичная страница показала `paused`,** потому что сценарий `live`
  ставил проверку на паузу. Это правильное поведение продукта, сценарий
  переписан: проверка работает.
- **Максимальная задержка старта 42 с в `load`** оказалась хвостом
  предыдущего сценария: окно статистики планировщика — 5 минут, и в него
  попадал перезапуск backend из `restart`. Поэтому в `load` добавлена
  независимая мера по журналу эмулятора, а в выводе рядом со статистикой
  планировщика написано про окно в 5 минут.

**Как проверено:** полный прогон `node scripts/verify.mjs` — 10 из 10,
код выхода 0.
